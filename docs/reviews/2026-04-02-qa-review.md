# QA 리뷰

- 날짜: 2026-04-02
- 리뷰 관점: `qa-review`
- 대상 범위: `codex/departure-board` 브랜치의 현재 `mini-react` 프로젝트
- 전제: hooks는 루트 전용 모델로 유지하는 것이 팀의 의도다

## 전체 판단

현재 테스트 분포는 나쁘지 않습니다. 핵심 단위 기능과 hooks 동작의 기본 시나리오는 상당 부분 자동화되어 있습니다. 다만 QA 관점에서 지금 신뢰도를 낮추는 요소가 분명히 있습니다. 실제로 통합 테스트 1개가 환경 의존성 때문에 실패하고 있고, 함수형 updater 같은 중요한 회귀 포인트는 아직 직접 검증하지 않으며, `useEffect`의 unmount cleanup처럼 라이프사이클 끝단 시나리오도 비어 있습니다.

## 핵심 QA 이슈

### 1. `hooks-demo` 통합 테스트가 현재 팀 공통 환경에서 안정적으로 통과하지 않습니다

실제 테스트 실행 결과 전체 44개 중 43개는 통과했지만, `hooks-demo` 통합 테스트 1개는 실패합니다. 실패 원인은 구현 동작보다 테스트 자체가 특정 로컬 절대 경로에 의존하기 때문입니다.

관련 파일:

- [hooks-demo.test.js](/D:/03Dev/05Jungle/mini_react/mini_react/test/hooks-demo.test.js#L231)

문제 영향:

- 팀원이 같은 저장소를 받아도 같은 결과를 보장할 수 없습니다.
- CI에 올리면 green 기준 자체가 흔들립니다.
- 가장 사용자 흐름에 가까운 테스트가 신뢰 지표로 기능하지 못합니다.

현재 확인된 결과:

- 전체 테스트: 44개
- 통과: 43개
- 실패: 1개
- 실패 테스트: `hooks demo mounts and updates state through real button handlers`
- 실패 원인: 절대 경로 import로 인한 `ERR_MODULE_NOT_FOUND`

QA 관점 판단:

- 이 테스트는 “있다”보다 “항상 같은 방식으로 통과한다”가 더 중요합니다.
- 지금 상태에서는 통합 테스트 커버리지가 있는 것처럼 보여도 실제 회귀 방어력이 낮습니다.

### 2. 함수형 updater의 핵심 회귀 시나리오를 직접 검증하는 테스트가 없습니다

현재 `useState` 테스트는 초기값, setter 참조 안정성, 다중 슬롯 독립성은 잘 보고 있습니다. 하지만 `setState((prev) => ...)` 형태의 함수형 updater가 정확히 한 번 호출되는지는 직접 검증하지 않습니다.

관련 파일:

- [hooks.test.js](/D:/03Dev/05Jungle/mini_react/mini_react/test/hooks.test.js)
- [hooks.js](/D:/03Dev/05Jungle/mini_react/mini_react/src/hooks.js#L110)

리스크:

- 함수형 updater는 hooks에서 가장 회귀가 잘 나는 지점 중 하나입니다.
- 현재 구현에서 updater가 두 번 평가될 여지가 있어도, 지금 테스트 세트로는 바로 잡히지 않습니다.
- 결과값만 맞는 테스트는 부수 효과나 호출 횟수 문제를 놓칠 수 있습니다.

QA 관점 판단:

- 이건 단순 추가 테스트가 아니라 회귀 방지용 핵심 테스트입니다.
- 실제 사용 패턴과도 가까워서 우선순위가 높습니다.

### 3. `useEffect` cleanup의 unmount 시나리오가 자동화되어 있지 않습니다

현재 테스트는 dependency 변경 시 cleanup이 먼저 호출되는지는 확인합니다. 하지만 컴포넌트가 제거될 때 cleanup이 호출되는지, 또는 루트가 사라질 때 effect 정리가 되는지는 보이지 않습니다.

관련 파일:

- [hooks.test.js](/D:/03Dev/05Jungle/mini_react/mini_react/test/hooks.test.js#L284)
- [render.test.js](/D:/03Dev/05Jungle/mini_react/mini_react/test/render.test.js)

리스크:

- 라이프사이클 종료 시 정리 누락은 나중에 메모리, 타이머, 이벤트 해제 문제로 이어질 수 있습니다.
- 지금은 학습 프로젝트라도, hooks 데모를 계속 확장하면 이 지점이 버그 보고서로 돌아올 가능성이 있습니다.

QA 관점 판단:

- dependency 변경 cleanup만으로는 충분하지 않습니다.
- “사라질 때도 정리되는가”는 별도 시나리오로 테스트하는 것이 좋습니다.

## 가정과 불확실한 점

- 이번 리뷰는 hooks의 설계 범위를 문제 삼지 않고, 현재 의도된 모델 안에서 테스트 신뢰도만 봤습니다.
- 테스트 실행은 권한 상승 환경에서 확인했습니다.
- README 인코딩 문제는 사용자 문서 품질 이슈이지만, 이번 문서에서는 테스트 신뢰도보다 우선순위를 낮게 두었습니다.
